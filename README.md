# test_tspu — Mihomo + m-ui на VPS

Один файл `deploy.sh`, **Ubuntu 22.04/24.04**, без Docker и без клонирования репозитория.
Устанавливает Mihomo `v1.19.34`, m-ui `v0.3.3`, применяет проверяемые настройки BBR/очередей/лимитов и настраивает HTTPS для GUI.

## Установка

```bash
curl -fsSL https://raw.githubusercontent.com/detektor133/test_tspu/main/deploy.sh -o deploy.sh
sudo bash deploy.sh
```

**По умолчанию** определяется публичный IPv4 VPS, на него выпускается короткоживущий сертификат Let's Encrypt (~6 дней). GUI доступен по `https://IP:2053/<случайный-путь>` с логином и паролем, которые выдаёт установщик.

**С доменом:** сначала направьте DNS A-запись на IPv4 VPS, затем:

```bash
sudo bash deploy.sh --domain panel.example.com
```

**С указанным IP:**

```bash
sudo bash deploy.sh --ip 203.0.113.10
```

Требуется **реальный публичный IPv4**, открытые снаружи **TCP 80** (проверка Let's Encrypt) и **TCP 2053** (GUI), включая firewall самого VPS и сетевой firewall хостера. Порт 80 не должен быть занят другим процессом. IP в примере — зарезервированный для документации, не используйте его буквально.

**Если выпуск сертификата не удался, установщик завершится с ошибкой, не открывая HTTP-панель наружу.** Учётные данные генерируются на VPS и не сохраняются в Git.

## Повторный запуск и обновления

`deploy.sh` можно запускать повторно после каждого обновления репозитория. Он сверяет фактическое состояние VPS с требуемым: зависимости, `sysctl`, версии Mihomo/m-ui, лимиты systemd, TLS, GUI и таймер проверки IP. Совпадающее не трогает, недостающее восстанавливает, отличающееся обновляет. Повторный запуск без изменений **не перезапускает m-ui**.

Версии Mihomo и m-ui закреплены в самом установщике. При их изменении новый бинарник скачивается с проверкой SHA256, а m-ui обновляется с резервным копированием данных через upstream-установщик. При ошибке запуска после замены Mihomo предыдущий бинарник восстанавливается, если он был. Секреты и пользовательские подключения m-ui не пересоздаются.

В конце выводится количество изменений либо `Итог: без изменений`. Диагностика: `sudo bash deploy.sh --check`. Автотесты проверяют нулевой повторный запуск по PID процесса, восстановление удалённых настроек и повреждённых бинарников.

## Бесплатный домен DuckDNS и автоматические подключения

Один раз зарегистрируйте поддомен на [DuckDNS](https://www.duckdns.org/) и сохраните токен в файл, доступный root (не в репозитории):

```bash
sudo install -m 0600 /dev/null /root/duckdns.token
sudo nano /root/duckdns.token  # вставьте токен DuckDNS
sudo bash deploy.sh --duckdns example.duckdns.org --duckdns-token-file /root/duckdns.token
```

Первый запуск обновит A-запись на публичный IPv4 VPS, запросит TLS-сертификат для поддомена, установит и настроит Mihomo/m-ui. **TCP 80** должен быть доступен извне для выпуска HTTPS, **TCP 2053** — для веб-панели. Изменения DNS могут распространяться не сразу; в таком случае повторите деплой. Токен копируется в `/var/lib/test-tspu/duckdns-token` с правами `0600`. При повторных запусках аргументы DuckDNS не нужны: таймер проверяет IP и обновляет запись автоматически. Секрет не публикуется и не выводится в логах.

После установки деплой создаёт через API m-ui недостающие inbounds:

| Протокол | Слушатель |
|---|---|
| VLESS + REALITY | 443/TCP |
| Hysteria2 | 14443/UDP |
| TUIC v5 | 8443/UDP |
| Shadowsocks | 8388/TCP и UDP |
| Trojan | 9443/TCP |
| AnyTLS | 10443/TCP |
| VLESS + XHTTP + TLS | 11443/TCP |

Порты **443/TCP и 443/UDP не совмещены**, поскольку m-ui v0.3.3 проверяет уникальность номера порта на уровне inbounds, даже для разных транспортов. Для REALITY выбирается доступный TLS-сайт с корректным сертификатом. Если ни один кандидат не прошёл проверку — REALITY пропускается с сообщением. Можно передать `--reality-target www.example.com` (сайт должен быть реально доступен).

У всех созданных inbound есть собственный случайный пароль/UUID. Секреты остаются на VPS (`/var/lib/test-tspu/inbound-secrets.json`, `0600`), а сами подключения и клиенты видны в m-ui. **Повторный запуск пропускает существующие inbound по имени и не сбрасывает клиентские настройки.** После создания новые listeners применяются через API перезапуска ядра. Для клиентов используйте ссылки и подписки m-ui.

На уже установленной панели пароль администратора не сбрасывается. Если установка была выполнена старой версией скрипта, передайте текущий пароль файлом:

```bash
sudo bash deploy.sh --panel-password-file /root/m-ui-password
```

Скрипт сохранит учётные данные в root-only файлах для последующих запусков. При ручной смене пароля повторите указание файла. Автоматическое создание inbounds можно отключить параметром `--no-inbounds`.

Нужны разрешения cloud firewall для соответствующих TCP/UDP портов. Правила UFW, если он активен, установщик добавляет; реальную доступность протоколов из России проверяем отдельно.

## Смена IP

Автоматическая проверка по таймеру `test-tspu-ip-check.timer` после загрузки и примерно каждые 30 минут:

- Если IP прежний — ничего не делает.
- Если изменился — пробует выпустить сертификат на новый IPv4 и перенастроить m-ui.
- Если проверка Let's Encrypt не удалась — старый адрес остаётся в настройках; попытка повторится. Нужны доступность нового IP снаружи и порт TCP 80.

Проверить вручную:

```bash
sudo /usr/local/sbin/test-tspu-deploy --sync-ip
# Или явно указать новый адрес
sudo /usr/local/sbin/test-tspu-deploy --sync-ip --ip НОВЫЙ_IP
```

Для домена при смене IP обновляйте DNS A-запись. Сертификат остаётся действительным для **имени домена**, если он не истёк; m-ui обновляет его через acme.sh.

**Продление:** m-ui устанавливает `acme.sh`, который регистрирует задачу в cron. Для IP-сертификатов необходимо частое автоматическое обновление, так как они действуют около шести дней.

## Диагностика

```bash
sudo /usr/local/sbin/test-tspu-deploy --check
systemctl status m-ui test-tspu-ip-check.timer --no-pager
journalctl -u m-ui -n 40 --no-pager
```

UFW не включается автоматически, чтобы не потерять SSH. При его включении установщик сохраняет указанный SSH-порт и открывает TCP 80/2053:

```bash
sudo bash deploy.sh --firewall --ssh-port 22
```

Перед установкой желательно сделать снимок VPS. Рост производительности от BBR и сетевых настроек **не гарантируется**, проверяем до/после. Веб-панель управляет Mihomo, но протоколы и клиенты создаются отдельно через GUI.

## Автоматические тесты

GitHub Actions запускает реальные установки на **Ubuntu 22.04 и 24.04**. Проверяет бинарники Mihomo и m-ui, systemd, HTTPS-страницу входа, повторный деплой, переход между IP и доменом, сохранение состояния при ошибке обновления и откат настроек. Лимит исполнения интеграционного сценария — **170 секунд** (не считая запуска runner).

Для HTTPS в CI используется **временный локальный CA**, а перевыпуск через Let's Encrypt **имитируется**. Дополнительные аргументы `--cert-file`, `--key-file`, `--ca-cert` позволяют проверить реальный TLS без публичного VPS.

**В GitHub Actions нельзя проверить:** доступность сертификатного HTTP-01 с интернета, реальный выпуск/продление Let's Encrypt, сетевую фильтрацию и смену публичного IP у провайдера. Это остаётся задачей испытаний на целевом VPS.
