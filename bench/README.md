# Полевые измерения Android/Termux → VPS для тестового AnyModel

Здесь **три разных эксперимента**, а не одна команда на все случаи.
Телефон получает HTTP-ответ от **loopback origin на своём VPS**
через локальный Mihomo и выбранный VPN-протокол.
Компьютер и USB/ADB не участвуют в тестовом трафике; SSH с телефона
используется только для запуска origin и независимого монитора на VPS.

## Установка и безопасность

На телефоне Termux из F-Droid или официального GitHub:
```bash
pkg install -y git
git clone https://github.com/detektor133/test_tspu.git
cd test_tspu
bash bench/setup_termux.sh
python bench/phone.py configure
```
Если уже установлен: `cd ~/test_tspu && git pull --ff-only origin main`.
`configure` спрашивает ссылку Mihomo/Clash из приватного
`/var/lib/test-tspu/subscriptions.txt` на VPS и сохраняет её только
локально на телефоне (0600). **Не отправляйте эту ссылку в чат, GitHub
или отчёт.**

С самого Termux нужен SSH-ключ, которому доверяет VPS:
```bash
ssh -o BatchMode=yes root@ВАШ_IPV4 'echo SSH-OK'
```
Если по ключу не работает, создайте `ssh-keygen -t ed25519` и добавьте
только файл `~/.ssh/id_ed25519.pub` в авторизованные ключи VPS.
Сверьте fingerprint сервера. Другого пользователя/порт задайте
`--ssh-user` и `--ssh-port`. Монитору на VPS нужен Linux AF_PACKET
(CAP_NET_RAW); он собирает **только агрегаты пакетов**, не payload/токены.
Source IPv4 совпадает с IP управляющей SSH-сессии — при расхождении
CGNAT возможен честный `route_no_ingress`, а не подстановка чужих данных.

Перед испытанием отключите системный VPN на телефоне и энергосбережение
Termux. На SberMobile выключите Wi-Fi, на Ростелекоме выключите мобильные
данные. `--network` — метка, не автоматическое доказательство провайдера.

## Режим A: smoke — не нагрузочный бенчмарк

Проверяет все 7 протоколов, SHA256 и nonce ответа, два отрицательных
контроля (DIRECT и сломанный SOCKS5) и входящий пакет на порту VPS.
**Не рассчитывает p95**, поскольку 2–3 загрузки ничего о хвосте задержек
не говорят. По умолчанию 1 поток, 5 секунд, до 16 МиБ резервируемой
полезной нагрузки.

```bash
python bench/phone.py run --vps ВАШ_IPV4 --network sbermobile --mode smoke
```

Для дополнительных попыток:
```bash
python bench/phone.py run --vps ВАШ_IPV4 --network sbermobile \
  --mode smoke --levels 1,2,4 --max-mib 32
```

Успешный `smoke_pass` говорит только о работоспособности выбранного пути.
`smoke_degraded` — хотя бы один ошибочный ответ, но есть успешная передача.
`route_no_ingress` / `route_ambiguous` не объявляются успешными.

## Режим B: load — сравнимые ступени нагрузки

Выбираем несколько кандидатов (по умолчанию REALITY, Hysteria2, TUIC),
даём каждому ступени 1, 4, 8, 16 одновременных загрузок **по 60 секунд**.
Каждая ступень проверяет реальный `peak_inflight`, ошибки, скорость
действительно завершённого HTTP-трафика, CPU/RSS VPS.
Параллельно отдельный `/ping` (нулевой body) оценивает прикладную
задержку через туннель. Это **не ICMP RTT** и **не время скачивания**.

```bash
python bench/phone.py run --vps ВАШ_IPV4 --network sbermobile \
  --mode load --protocols reality,hy2,tuic \
  --levels 1,4,8,16 --seconds 60 --max-mib 768
```

**Трафик:** до 768 МиБ полезной нагрузки плюс HTTPS/VPN/SSH и ping.
Используйте при достаточном мобильном тарифе. Начните с одного кандидата,
если трафик ограничен:
```bash
python bench/phone.py run --vps ВАШ_IPV4 --network sbermobile \
  --mode load --protocols reality --levels 1,4,8 \
  --seconds 60 --max-mib 256
```

Затем повторите с **теми же параметрами** на Wi-Fi Ростелекома:
```bash
python bench/phone.py run --vps ВАШ_IPV4 --network rostelecom \
  --mode load --protocols reality --levels 1,4,8 \
  --seconds 60 --max-mib 256
```

### Метрики и критерии

- **Throughput** — проверенные HTTP-байты / фактическое время полного
  интервала; это не заявленная пропускная способность сети.
- **HTTP ping p50** рассчитывается по всем успешным /ping в нагрузке.
  **HTTP ping p95** — только при 20+ успешных измерениях, p99 — при
  100+; всегда показываем фактическое `n` и тайм-ауты. При n=20 оценка
  p95 по ближайшему рангу равна максимуму: повторные длинные серии
  гораздо надёжнее для выводов о хвостовых задержках.
- Если у клиента длинные задержки и за 60 секунд удалось выполнить
  только 12 ping, в отчёте будут p50, n=12, p95=«—». **Скорость при
  этом остаётся валидной**, если выполнены её независимые критерии.
  Для изучения p95 увеличьте `--seconds` до 120 или используйте soak.
- `ok` означает подтверждённый порт VPS, независимые отрицательные
  контроли, завершённый интервал, 20+ успешных загрузок, ≥95%
  успешных HTTP-запросов, реально достигнутую параллельность.
  `degraded` фиксирует потери выше порога.
  `budget_limited` — трафик кончился раньше времени.
  `underfilled_concurrency` — задано больше потоков, чем достигнуто.
- `verified_with_noise` означает, что на ожидаемом порту действительно
  есть пакеты с внешнего IP телефона, а на других портах видны лишь
  единичные остаточные пакеты. Сильная одновременная активность
  помечается `route_ambiguous` и не признаётся валидным маршрутом.

Параметры: `--protocols all` либо
`reality,xhttp,hy2,tuic,ss,trojan,anytls`; `--levels` до 7 различных
значений 1–64; `--seconds` 2–900 (load ≥20);
`--ping-interval` 0.1–5 секунд (по умолчанию 0.2, интервал
между завершением пингов); `--payload-kib` 64/128/256/512/1024/2048/4096;
`--min-success-pct` по умолчанию 95.

**Бюджет никогда не «растягивается» искусственно до нужного времени.**
Если при быстром протоколе квота заканчивается за 20 секунд вместо 60,
будет `budget_limited` и эта строка не будет считаться полноценным
замером пропускной способности за заданный интервал.

## Режим C: soak — устойчивость и возможная деградация по объёму

Один протокол, 4 параллельных потока, 180 секунд и до 512 МиБ —
настраивается по необходимости. Сохраняются **каждые 10 секунд**:
сколько завершено загрузок, ошибки, подтверждённые байты,
приближённая скорость завершений, сколько HTTP ping выполнилось
и их медиана. Это позволяет заметить ухудшение после определённого
объёма успешной нагрузки, **но не доказывает причину (ТСПУ)**.

```bash
python bench/phone.py run --vps ВАШ_IPV4 --network sbermobile \
  --mode soak --protocols reality --levels 4 \
  --seconds 180 --max-mib 512
```

Повторите серию через Ростелеком и в другое время суток. Если нужно
изучить порог блокировки, сравнивайте `time-windows.csv`,
`protocol_cumulative_mib`, потери и CPU/RAM, не выдавая одиночный
скачок графика за доказательство DPI.

## Что формируется

Приватный `~/test-tspu-results/<дата-сеть-id>`:
`measurements.csv` (сводные уровни), `request-samples.csv` (все
загрузки и ping с nonce), `time-windows.csv` (10-секундные интервалы),
`negative-controls.json`, `environment.json`, `server-resources.csv`,
`report.md`, `charts/*.svg`. Для soak дополнительно
`charts/time-windows.svg`.

**Секретные** `private-mihomo.yaml` и `mihomo.log` не экспортируются.

```bash
termux-setup-storage
python bench/export_results.py ~/test-tspu-results/ПАПКА_ПРОГОНА
```
На Windows: `adb pull /sdcard/Download/test-tspu-results/`.
Это копирование отчёта, а не транспорт нагрузочных HTTP-запросов.

Сравнить **две сети, одинаковые нагрузочные режимы и параметры**:
```bash
python bench/compare_runs.py \
  ~/test-tspu-results/ПАПКА_SBER \
  ~/test-tspu-results/ПАПКА_ROSTELECOM \
  --output ~/test-tspu-results/compare-networks.md
```
Сравнение не смешивает smoke и load, а короткие / невалидированные
ступени исключаются из графиков. Если для p95 недостаточно наблюдений,
скорость не обнуляется, и это явно указано в таблице.

### Ограничения и сдача

Тестовый origin доступен только через VPS loopback; SSH-контроль — отдельная
зависимость, его блокировка не говорит о блокировке самого VPN.
Счётчики портов измеряют **входящие пакеты от телефона**, но загруженные
данные в основном идут с VPS **наружу**, поэтому их IP-байты нельзя
приравнивать к объёму скачивания. Искажённый сигнал, CGNAT, общий VPS,
перегрузка CPU/канала или смена маршрута дают альтернативные объяснения
ошибкам. CI тестирует код и протоколы на контролируемом стенде, не российский
ТСПУ. Для задания AnyModel отдельно нужны: описание картины фильтрации,
гипотеза выбранного протокола и её риски, данные двух сетей,
конкретная рабочая подписка/QR, стоимость VPS, время выполнения и
работающий сервер на 7 дней после сдачи. Не публикуйте токены и
приватные профили в открытом репозитории.


### Почему REALITY называется Vision

В `deploy.sh` серверный VLESS REALITY слушает TCP/443 с
`flow: xtls-rprx-vision`. При полевом запуске профиль с этим портом
обязательно проверяется и на Android: наличие `flow=xtls-rprx-vision`
и `reality-opts` в клиентской подписке. Это **VLESS + REALITY +
XTLS Vision**, а не любой VLESS по порту 443. В CI для клиентской
подписки тоже добавлена такая проверка.

Если хотя бы один режим успешно передал данные, но экспорт результатов
завершился исключением, это **ошибка всей прогонки как артефакта**:
нельзя считать отчёт готовым, пока данные не записаны. Поля
независимого счётчика и CSV синхронизированы единым `EVIDENCE_FIELDS`;
регрессионный тест проверяет запись различных состояний сети в CSV.
