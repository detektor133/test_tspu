# Аудируемый полевой бенчмарк Android/Termux → собственный VPS

Основа задания AnyModel: **проверить реально работающий туннель**, измерить
пропускную способность, прикладную задержку **под нагрузкой**, CPU/RAM VPS,
наблюдаемую параллельность и динамику качества по мере передачи данных.
Результаты SberMobile и Ростелекома сравниваются только при одинаковой методике.
**GitHub Actions не моделирует ТСПУ РФ.** Только полевые замеры дают цифры для отчёта.

Модель измерения: `Android (без системного VPN) → локальный Mihomo HTTP-proxy
→ выбранный VPN-протокол → VPS → HTTP origin на 127.0.0.1:18180`.
Обычный SSH от самого Android используется **исключительно для управления**
origin, серверным монитором и пассивными счётчиками пакетов; через него
не идут HTTP-нагрузка или ping. Windows/ADB могут управлять Termux, но не
переносят тестовый трафик.

## Установка

Termux из [F-Droid](https://f-droid.org/en/packages/com.termux/) либо
официального [GitHub](https://github.com/termux/termux-app).
В Termux:

```bash
pkg install -y git
git clone https://github.com/detektor133/test_tspu.git
cd test_tspu
bash bench/setup_termux.sh
python bench/phone.py configure
```

Для уже клонированного репозитория достаточно
`cd ~/test_tspu && git pull --ff-only origin main`.
`configure` запрашивает секретный URL **Mihomo/Clash** из
`sudo cat /var/lib/test-tspu/subscriptions.txt` на собственном VPS.
Ссылка остаётся в приватном файле телефона (0600), не вставляйте её в отчёт/чат.

На телефоне требуется SSH-доступ по ключу к **публичному IPv4 VPS**.
В Termux:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub
```

Добавьте **только публичный ключ** в `/root/.ssh/authorized_keys` на VPS
через уже доверенную сессию. Проверьте fingerprint сервера и отсутствие
запроса пароля:

```bash
ssh root@ВАШ_IPV4 'echo SSH-OK'
ssh -o BatchMode=yes root@ВАШ_IPV4 true
```

По умолчанию используется `root@ВАШ_IPV4:22`. Если провайдер ограничивает
CAP_NET_RAW/AF_PACKET, новая проверка **остановится с явной ошибкой**:
подменять независимый учёт пакетов ответом API Mihomo запрещено.
Чтобы подтвердить пакеты, SSH-клиент и VPN-туннель должны выходить в
интернет с **одного внешнего IPv4** телефона (включая CGNAT): сборщик
учитывает только входящие IPv4-пакеты с адреса управляющей SSH-сессии.

## Что действительно проверяется

1. Временный origin на VPS привязан к loopback, выдаёт случайную полезную
   нагрузку (стандартно 256 КиБ) и отвечает на `/ping` нулевым телом.
   Каждый ответ подтверждает индивидуальный nonce; скачивание дополнительно
   проверяется по SHA256 и размеру.
2. **Отрицательные контроли:** `DIRECT` и заведомо сломанный SOCKS5
   не должны получить origin. Если хоть один смог — **остановка**;
   цифры остальных протоколов не признаются.
3. Пассивный `AF_PACKET` на VPS считает **только суммарное число
   входящих пакетов и IP-байт** с исходящего IPv4 телефона и по
   порту/транспорту конкретного протокола. Без payload, клиентских IP
   в отчёте, токенов и секретов. Если пакеты не наблюдаются —
   `route_no_ingress`. Если за время ступени есть трафик на других
   тестовых портах — `route_ambiguous`.
4. Для каждой ступени фиксируются `peak_inflight` (реальное количество
   одновременно работающих запросов), длительность, байты, ошибки,
   throughput, p50/p95/p99 скачивания и **отдельно** HTTP /ping во время
   загрузки, плюс CPU/RSS Mihomo/m-ui на VPS.
5. В `request-samples.csv` есть каждый запрос и ping с временем,
   результатом и nonce. Генератор отчёта повторно проверяет сумму
   запросов/байт, уникальность nonce, соответствие контролям и доказательствам
   маршрута. Старые CSV не превращаются задним числом в проверенные измерения.

`HTTP /ping` — **прикладное время запрос–ответ через прокси**, включая
создание соединения и путь до origin. **Это не ICMP RTT и не время
скачивания 256 КиБ**. Для p95 нужны минимум 20 успешных выборок,
для p99 — 100. Малое число проб даёт «н/д», а не ложный процентиль.

Статусы: `ok` (полный интервал, подтверждённая трасса, достаточные
выборки, достигнутая параллельность), `budget_limited` (квота оборвалась
раньше времени), `insufficient_samples`, `insufficient_rtt_samples`,
`underfilled_concurrency`, `failed`, `route_no_ingress`,
`route_ambiguous`. Только `ok` попадает на сравнительные графики.

## Запуск с мобильной сети и Wi-Fi

На Android выключите **системный VPN**, оставьте Termux активным,
отключите энергосбережение Termux. Для SberMobile выключите Wi-Fi;
для Ростелекома выключите мобильные данные. Параметр `--network` — это
метка, а не программное доказательство оператора.

**Минимальный smoke-test** (проверка маршрутов, не полноценной скорости;
до 32 МиБ полезной нагрузки плюс накладные расходы):

```bash
cd ~/test_tspu
python bench/phone.py run --vps ВАШ_IPV4 --network sbermobile \
  --levels 1,2,4 --seconds 6 --max-mib 32 --payload-kib 256
```

**Полевой профиль для сравнения сетей** (может потратить до 1024 МиБ
полезной нагрузки на каждую сеть, запускать при достаточном тарифе):

```bash
python bench/phone.py run --vps ВАШ_IPV4 --network sbermobile \
  --levels 1,2,4,8 --seconds 45 --max-mib 1024 --payload-kib 256
```

Те же `--levels`, `--seconds`, `--max-mib`, `--payload-kib`
используйте через Wi-Fi:

```bash
python bench/phone.py run --vps ВАШ_IPV4 --network rostelecom \
  --levels 1,2,4,8 --seconds 45 --max-mib 1024 --payload-kib 256
```

Для оценки больших уровней при необходимости отдельно используйте
`--levels 8,16,32,64`, но **не называйте 64 подтверждённым пределом**,
пока `peak_inflight`, интервал, потери и ресурсы не прошли проверку.
Заданы максимумы: 7 уникальных уровней по 1–64 потока, 3–120 секунд,
8–4096 МиБ полезной нагрузки, `--payload-kib` 64–4096 из разрешённых
двоичных размеров. `--payload-kib 1024` позволяет отдельно смотреть
на передачу более крупных файлов, а не только на скорость серии коротких
HTTP-запросов.

**Внимание к бюджету.** `--max-mib` ограничивает число резервируемых
полных ответов origin; реальный мобильный расход выше (TLS, VPN,
HTTP-заголовки, контрольные попытки, ping, SSH). При исчерпании квоты
ступень закончится раньше времени и не попадёт на график как полноценный
бенчмарк. 45 секунд не гарантируют 20 успешных /ping при задержках в секунды.
Увеличивайте длительность или повторяйте испытания, сохраняя исходные CSV.

## Получение данных и сравнение

Скрипт создаёт каталог `~/test-tspu-results/<дата-сеть-id>/`:
`measurements.csv`, `request-samples.csv`, `negative-controls.json`,
`server-resources.csv`, `environment.json`, `report.md`,
`charts/throughput.svg` и `charts/latency.svg`.
`private-mihomo.yaml` и `mihomo.log` — **приватные**, их нельзя
публиковать. Доступ к приватному каталогу ограничен владельцем.

```bash
termux-setup-storage
python bench/export_results.py ~/test-tspu-results/КАТАЛОГ_ПРОГОНА
```

В Windows PowerShell: `adb pull /sdcard/Download/test-tspu-results/`.
ADB здесь служит только для копирования разрешённых файлов, не для
интернет-трафика теста. Отчёт можно пересобрать
`python bench/generate_report.py КАТАЛОГ_ПРОГОНА`.

```bash
python bench/compare_runs.py \
  ~/test-tspu-results/КАТАЛОГ_SBER \
  ~/test-tspu-results/КАТАЛОГ_ROSTELECOM \
  --output ~/test-tspu-results/compare-networks.md
```

Сравниваются только подтверждённые ступени при одинаковых секундах,
размере ответа, частоте ping и ступенях. Неуспешные и короткие уровни
остаются видимыми как несопоставимые.

## Интерпретация результатов и ограничения

- Портовые счётчики независимы от API Mihomo и от HTTP origin, но не
  являются криптографическим доказательством аутентичности протокола.
  Подсчёт идёт по внешнему IPv4 телефона, поэтому если CGNAT даст разные
  адреса для SSH и VPN, программа честно не подтвердит порт.
- Входящие IP-байты на порт — это **не полный объём скачанных данных**:
  при скачивании payload в основном передаётся с VPS наружу.
- Скорость считается по проверенным полезным HTTP-байтам / фактическое
  время нагрузки. Это throughput рабочего клиента с новыми HTTP-сеансами,
  **не** максимум IP/TCP/UDP канала.
- Профили используют Mihomo на обеих сторонах. Измерения другого клиента
  могут отличаться. Внутренние HTTP-запросы теста идут не через Windows.
- Для выводов о фильтрации нужны повторные испытания в обеих сетях, в
  разные часы, с контролем состояния VPS, IP и уровня сигнала. Падение
  скорости после объёма `protocol_cumulative_mib` — наблюдение, **не
  автоматическое доказательство вмешательства ТСПУ**.
- В отчёт для тестового задания отдельно допишите выбор хостера, стоимость,
  реальное время разработки и обоснование протокола. Передавайте рабочий
  профиль/QR приватно. Оставьте VPS активным 7 дней после сдачи.
