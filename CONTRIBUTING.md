# Правила внесения изменений

## Ветки и коммиты

1. `main` — стабильная ветка. **Не отправлять исправления напрямую в `main`**.
2. Создать рабочую ветку от актуальной `main`: `feat/...`, `fix/...` или `test/...`.
3. Работать и исправлять ошибки **в рабочей ветке**. Названия коммитов и PR писать на русском.
4. Открыть Pull Request в `main`. Красные проверки исправлять в PR, а не дополнительными коммитами в `main`.
5. Сливать в `main` **только зелёный PR**, используя **Squash and merge** и одно осмысленное русское название итогового коммита. Проверить, что исходная ветка актуальна относительно `main`.

## Проверки перед слиянием

Перед слиянием должны быть зелёными все шесть проверок GitHub Actions:

- `Bash + ShellCheck`;
- `Установка и HTTPS (ubuntu-22.04)`;
- `Установка и HTTPS (ubuntu-24.04)`;
- `Установка и HTTPS (ubuntu-26.04)`;
- `Установка и HTTPS (debian-12)`;
- `Установка и HTTPS (debian-13)`.

Интеграционный этап ограничен `170s` (запуск runner и checkout в этот лимит не входят). Он проверяет установку, HTTPS, повторный деплой, клиентов, проброс реального HTTP-трафика через каждый протокол и имитацию DuckDNS. **Зелёный CI не означает, что подтверждена работа против ТСПУ** или выпуск публичного Let's Encrypt.

Если после слияния `main` всё-таки красный, сначала исправить регрессию отдельным PR; не продолжать разработку новых функций.

## Безопасность

Не загружать в репозиторий реальные пароли, приватные ключи, токены DuckDNS, URLs подписок и логи с секретами. При тестировании использовать только временные тестовые данные. При изменении протоколов не перезаписывать пользовательские inbound и токены подписок без явного согласия.

## Настройки GitHub (выполняются владельцем)

Это правило должно быть **технически обеспечено**, а не просто записано в Markdown:

1. В `Settings → Rules → Rulesets` создать активный *branch ruleset* для `main`.
2. Включить **Require a pull request before merging** и **Require status checks to pass**, выбрав шесть проверок выше.
3. Запретить force push, удаление защищённой ветки и обход правил.
4. В `Settings → General → Pull Requests` разрешить **Squash merging** и при необходимости отключить остальные способы слияния.

Без включённого ruleset прямые коммиты в `main` технически остаются возможными, даже если правила в документе описаны.
